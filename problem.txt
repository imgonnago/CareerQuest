CareerQuest 문제점 · 수정할 부분 목록
=====================================
- 코드 수정이나 테스트 중에 발견한 문제를 여기에 적는다.
- 고친 항목은 제목 옆에 (해결)을 붙이고, 맨 위에 "해결" 블록으로 어떻게 처리했는지 요약한다.
    - 해결: 날짜, 한 줄 요약
      방법: 어디(파일·함수)를 어떻게 바꿨는지, 왜 그 방법인지
      확인: 고친 뒤 테스트 결과 (테스트 안 했으면 "미확인"), 남은 한계·연결 항목
- 번호는 재사용하지 않는다. 새 항목은 맨 아래에 추가한다.


[1] 네이버 요약(snippet)이 잘려서 핵심 근거가 빠짐
  - 발견: 2026-10-29, 요구사항 검색 테스트 (피지컬 AI 엔지니어, 검색어 5개)
  - 위치: engine/tools/naver.py
  - 내용: 실제 채용공고(제논·뉴빌리티·케어링·퀘스터 등)는 대부분 네이버 카페 결과였는데,
          본문을 수집하지 않으니 우대사항이 "…"로 잘린다. 가장 쓸모 있는 근거가 snippet 수준에 머무름.
  - 추가: 2026-10-29 피지컬 AI 2단계 테스트 2회차에서 선택 LLM이 고른 8건 중 6건이 네이버(요약만) — 가장 관련 높은 실제 공고가
          네이버 카페에 몰려 있음. 카카오 1순위로 바꿔도 이 직무는 여전히 핵심 근거가 요약 수준.
  - 메모: 네이버 robots.txt 정책상 본문 수집은 불가. 같은 공고를 원문(기업 채용 페이지 등)에서
          다시 찾는 방법을 검토해야 함.

[2] 본문 수집 대상 중 주제와 무관한 문서가 많음 (해결)
  - 해결: 2026-10-30, 검색 순위대로 수집하지 않고 LLM이 고른 문서만 본문 수집
    방법: pipeline/stage2_evidence.py — 계획 LLM은 검색만 하고(search_requirements max_fetch=0, 본문 수집 안 함),
          선택 LLM(select_docs, 새 대화)이 근거 풀 전체의 [D번호] 제목 목록에서 읽을 문서를 DocSelection JSON으로 최대 MAX_SELECT(8)개 고름.
          EvidencePool.fetch가 고른 문서 중 pending만 본문 수집. 메모의 재정렬 모델 대신 LLM 선택을 씀(별도 모델 없이 바로 가능).
    확인: 백엔드는 실제 공고(펄어비스·포트원·네이버) 위주로 고름. 데이터 분석가는 무관 문서가 섞이고 실행마다 흔들림 → [16]
  - 발견: 2026-10-29, 요구사항 검색 테스트
  - 위치: engine/tools/requirements.py (collect_candidates → fetch_texts 사이)
  - 내용: 본문을 수집한 카카오 문서 22건 중 요구·우대사항을 직접 담은 건 4~5건.
          나머지는 투자 뉴스, 정책 예산, 창업 인터뷰 등. 검색 순위 그대로 앞에서부터 수집하기 때문.
  - 메모: 재정렬 모델을 두 단계 사이에 넣어 title + snippet으로 순서를 다시 매긴 뒤 수집.

[6] LLM에게 보여 줄 도구 결과 형식이 정해지지 않음 (해결)
  - 해결: 2026-10-30, LLM 역할마다 보여 주는 형식을 따로 정함
    방법: pipeline/stage2_evidence.py EvidencePool — add가 doc_id마다 대화 안 번호(D1, D2 …)를 붙이고,
          계획·선택 LLM에는 render_titles("[D번호] 제목 (본문 가능/요약만)"), 읽기 LLM에는 render_doc
          ("[D번호] 제목 / 출처·작성일 / 본문 전체(없으면 요약)", 자르지 않음)을 줌. 프롬프트(prompts/stage2_evidence.py) docstring에 짝을 적음.
          (처음엔 pipeline/evidence.py에서 add가 본문까지 넣었으나 [9] 때문에 제목 목록으로 바뀜)
    확인: 2단계 테스트에서 D번호로 선택·카드 작성이 정상 동작. D번호 칸은 정규식 패턴으로 묶어야 제목을 안 붙여 씀
  - 발견: 2026-10-29, 요구사항 검색 도구 구현
  - 위치: engine/tools/requirements.py (RequirementSearchResult)
  - 내용: 지금은 pydantic 객체를 그대로 반환. 도구 호출 결과로 LLM에 넘길 텍스트 형식
          (문서 목록·본문·출처 표기)은 모델·프롬프트 확정 후 파이프라인 단계에서 정해야 함.

[7] LLM 최종 정리의 인용 번호가 실제 문서 내용과 맞지 않음 (해결)
  - 해결: 2026-10-30, 자유 서술 대신 인용이 붙은 근거 카드로 받고 코드가 원문과 대조
    방법: 읽기 LLM이 CardDraftList JSON(doc·category·company·item·quote)을 Ollama format으로 강제해 출력.
          pipeline/stage2_evidence.py verify가 quote를 공백·말줄임표·따옴표를 지우고(_norm) 본문(없으면 제목+요약)에 있는지 대조,
          있으면 doc_id·evidence_level을 붙인 EvidenceCard, 없으면 rejected로 버림. 띄어쓰기를 바꿔 옮기는 경우가 많아 공백은 무시.
    확인: 2026-10-30 테스트에서 백엔드 7장 중 4장, 데이터 분석가 18장 중 6장을 버림. quote만 대조하므로 item 지어내기는 못 막음 → [10]
  - 발견: 2026-10-29, LLM(qwen3.5:9b) ↔ 요구사항 검색 도구 루프 테스트 ("백엔드 개발자 신입", 도구 호출 3회)
  - 위치: (예정) engine/pipeline 근거 추출·정리 단계
  - 내용: 인용 15건을 키워드로 대조한 결과, 상당수가 해당 문서에 없는 내용.
          예) [D6](요약만 있음)에 Redis·MongoDB·Docker·AWS·TOEIC를 인용 → 문서엔 '정보처리'만 있음.
              [D9] SK텔레콤 공고에 Docker·AWS 인용 → 없음. [D19]에 GitHub·README 인용 → 없음.
          "Docker 경험 필수" 같은 문서에 없는 단정도 나옴. 모델이 사전 지식으로 쓰고 번호를 대충 붙이는 것.
  - 메모: README 설계대로 문서별 "상세 근거 카드"(인용 문장 그대로 + doc_id)를 먼저 만들게 하고,
          코드가 인용 문장이 실제 본문/요약에 있는지 문자열 대조로 검증(5단계)해야 함. 최종 정리는 카드만 보고 작성.

[8] 근거 대부분이 요약(snippet) 수준이라 LLM이 빈 곳을 추측으로 메움
  - 발견: 2026-10-29, 같은 테스트
  - 위치: engine/tools/requirements.py
  - 내용: 도구 호출 1회당 문서 20건 중 본문은 2건뿐(전체 55건 중 6건). 나머지는 200자 내외 요약이라
          모델이 요약에서 단서만 보고 나머지를 지어내는 경향 ([7]의 원인 중 하나). [1]·[2]·[4]와 연결.
  - 진행: 원인은 두 가지 — 네이버는 항상 요약만(20건 중 10건), 카카오도 max_fetch(파이프라인 3) 상한에 걸려 10건 중 7건이 pending으로 남음.
          → 검색 결과 순서를 카카오 1순위로 변경(requirements.py PROVIDER_ORDER). max_fetch 상향은 [9] 컨텍스트 문제와 함께 결정 필요.

[9] 도구 호출이 쌓이면 컨텍스트가 빨리 참 (해결)
  - 해결: 2026-10-30, 대화에 본문을 쌓지 않고 역할별 새 대화로 나눔
    방법: pipeline/stage2_evidence.py — 계획 LLM 대화에는 도구 결과로 제목 목록만 남김(본문 수집도 안 함).
          읽기 LLM은 새 대화에서 고른 문서만 읽고, _batches가 문서를 자르지 않고 READ_BUDGET_CHARS(4만 자 ≈ 2만 토큰) 안에서 문서째 묶어
          여러 번 호출. 혼자 넘는 문서는 단독 호출. 본문을 자르지 않는 원칙을 지키려고 줄이는 대신 나눔.
          llm.chat은 prompt_eval_count가 num_ctx에 닿으면 경고.
    확인: 2026-10-30 백엔드·데이터 분석가 테스트에서 num_ctx 경고 없음. 단독으로 num_ctx를 넘는 문서는 아직 처리 방법 없음(미확인)
  - 발견: 2026-10-29, 같은 테스트
  - 위치: engine/llm.py, (예정) engine/pipeline
  - 내용: 도구 3회(본문 6건, 요약 49건)에서 마지막 턴 입력이 22,665토큰 (num_ctx 32768).
          본문 하나가 1만 자를 넘는 경우도 있어 max_fetch=5로 3번 호출하면 넘칠 수 있음.
          Ollama는 넘친 입력을 경고 없이 앞에서 잘라낸다 (시스템 프롬프트가 날아갈 수 있음).
  - 메모: chat()에서 prompt_eval_count가 num_ctx에 닿으면 경고하도록 함.
          본문을 자르지 않는 원칙이므로, 문서 1건씩 별도 호출로 근거 카드를 만들고 대화에는 카드만 남기는 구조가 필요.

[10] 카드의 item이 quote 내용과 맞지 않아도 통과함
  - 발견: 2026-10-29, 근거 카드 추출 테스트 ("데이터 분석가 신입")
