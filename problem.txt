=====================================

[1] 네이버 요약(snippet)이 잘려서 핵심 근거가 빠짐
  - 발견: 2026-10-29, 요구사항 검색 테스트 (피지컬 AI 엔지니어, 검색어 5개)
  - 위치: engine/tools/naver.py
  - 내용: 실제 채용공고(제논·뉴빌리티·케어링·퀘스터 등)는 대부분 네이버 카페 결과였는데,
          본문을 수집하지 않으니 우대사항이 "…"로 잘린다. 가장 쓸모 있는 근거가 snippet 수준에 머무름.
  - 추가: 2026-10-29 피지컬 AI 2단계 테스트 2회차에서 선택 LLM이 고른 8건 중 6건이 네이버(요약만) — 가장 관련 높은 실제 공고가
          네이버 카페에 몰려 있음. 카카오 1순위로 바꿔도 이 직무는 여전히 핵심 근거가 요약 수준.
  - 메모: 네이버 robots.txt 정책상 본문 수집은 불가. 같은 공고를 원문(기업 채용 페이지 등)에서
          다시 찾는 방법을 검토해야 함.

  - 발견: 2026-10-29, 요구사항 검색 테스트
  - 위치: engine/tools/requirements.py (collect_candidates → fetch_texts 사이)
  - 내용: 본문을 수집한 카카오 문서 22건 중 요구·우대사항을 직접 담은 건 4~5건.
          나머지는 투자 뉴스, 정책 예산, 창업 인터뷰 등. 검색 순위 그대로 앞에서부터 수집하기 때문.
  - 메모: 재정렬 모델을 두 단계 사이에 넣어 title + snippet으로 순서를 다시 매긴 뒤 수집.

[3] 본문 추출 결과에 페이지 잡음이 섞임

  - 발견: 2026-10-29, LLM(qwen3.5:9b) ↔ 요구사항 검색 도구 루프 테스트 ("백엔드 개발자 신입", 도구 호출 3회)

          예) [D6](요약만 있음)에 Redis·MongoDB·Docker·AWS·TOEIC를 인용 → 문서엔 '정보처리'만 있음.
              [D9] SK텔레콤 공고에 Docker·AWS 인용 → 없음. [D19]에 GitHub·README 인용 → 없음.
          "Docker 경험 필수" 같은 문서에 없는 단정도 나옴. 모델이 사전 지식으로 쓰고 번호를 대충 붙이는 것.

[8] 근거 대부분이 요약(snippet) 수준이라 LLM이 빈 곳을 추측으로 메움
  - 발견: 2026-10-29, 같은 테스트
  - 위치: engine/tools/requirements.py
  - 내용: 도구 호출 1회당 문서 20건 중 본문은 2건뿐(전체 55건 중 6건). 나머지는 200자 내외 요약이라
          모델이 요약에서 단서만 보고 나머지를 지어내는 경향 ([7]의 원인 중 하나). [1]·[2]·[4]와 연결.
  - 진행: 원인은 두 가지 — 네이버는 항상 요약만(20건 중 10건), 카카오도 max_fetch(파이프라인 3) 상한에 걸려 10건 중 7건이 pending으로 남음.
          → 검색 결과 순서를 카카오 1순위로 변경(requirements.py PROVIDER_ORDER). max_fetch 상향은 [9] 컨텍스트 문제와 함께 결정 필요.

[9] 도구 호출이 쌓이면 컨텍스트가 빨리 참 (해결)
  - 해결: 계획 LLM 대화에는 제목 목록만 남기고, 읽기 LLM은 새 대화에서 문서를 자르지 않고 READ_BUDGET_CHARS 단위로 묶어 여러 번 호출
  - 발견: 2026-10-29, 같은 테스트
  - 위치: engine/llm.py, (예정) engine/pipeline
  - 내용: 도구 3회(본문 6건, 요약 49건)에서 마지막 턴 입력이 22,665토큰 (num_ctx 32768).
          본문 하나가 1만 자를 넘는 경우도 있어 max_fetch=5로 3번 호출하면 넘칠 수 있음.
          Ollama는 넘친 입력을 경고 없이 앞에서 잘라낸다 (시스템 프롬프트가 날아갈 수 있음).
  - 메모: chat()에서 prompt_eval_count가 num_ctx에 닿으면 경고하도록 함.
          본문을 자르지 않는 원칙이므로, 문서 1건씩 별도 호출로 근거 카드를 만들고 대화에는 카드만 남기는 구조가 필요.

[10] 카드의 item이 quote 내용과 맞지 않아도 통과함
  - 발견: 2026-10-29, 근거 카드 추출 테스트 ("데이터 분석가 신입")
  - 위치: engine/pipeline/evidence.py (verify)
  - 내용: 검증은 quote가 원문에 있는지만 본다. item은 LLM이 쓰는 칸이라 지어낼 수 있음.
          예) quote "…AI 툴 키워드가 포함된 공고는 170% 증가" → item "클로드, 제미나이, 챗GPT, 코파일럿, 미드저니"
              quote "…사무 역량을 보여주는 자격증입니다" → item "사무자동화산업기사, 컴퓨터활용능력"
  - 메모: item의 핵심 단어(자격증명·기술명)가 quote 안에 있는지도 대조하거나, item을 quote에서 뽑은 단어로 제한.

[16] 선택 LLM의 문서 선택 품질이 실행마다 흔들림
  - 발견: 2026-10-29, 같은 테스트
  - 위치: engine/prompts/stage2_evidence.py (SELECT_REQUEST)
  - 내용: 백엔드는 실제 공고(펄어비스·포트원·네이버) 위주로 잘 고름. 데이터 분석가는 농심 대졸 공채(영업·생산직),
          건축사무소 취업 가이드, 빅데이터 연봉 글처럼 직무와 먼 문서를 섞어 고름. 같은 직무라도 실행마다 다름.
          제목만 보고 고르므로 "OO 채용"류 제목은 직무 관련 여부를 판단하기 어려움.
  - 추가: 학생 질문을 입력에 넣자 검색어가 관점별로 다양해지고 선택도 좋아짐(피지컬 AI: 크래프톤·제논·뉴빌리티·케어링 공고).
          다만 같은 입력으로 2회 실행 시 검색 횟수(3/2회)·선택 문서·카드 수(25/7장)·시간(49/15초)이 크게 다름.
  - 메모: 사고 기능(think=True)을 켜면 품질이 좋아지지만 1.5초 → 약 28초. 제목 + 짧은 요약 일부를 같이 주는 실험은
          오히려 나빴음(무관한 공고 증가). 계획 LLM의 검색어가 거의 같은 것도 원인 — 3번 검색어가 모두 "…자격증 우대사항…" 변형.

[17] 읽기 LLM이 직무와 무관한 기업정보 카드를 대량 생성
  - 발견: 2026-10-29, 같은 테스트 (데이터 분석가: 통과 32장 중 22장이 농심·KT DS·건원엔지니어링 기업정보)
  - 위치: engine/prompts/stage2_evidence.py (READ_SYSTEM), engine/schemas/card.py (Category)
  - 내용: 공장 위치, 매출, 복리후생, 본사 주소 등 직무 근거가 아닌 내용까지 카드로 만듦. 프롬프트의
          "목표 직무와 관계없는 내용은 카드로 만들지 않는다"가 지켜지지 않음. [11]·[12]와 연결.
